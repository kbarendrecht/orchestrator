Review overlay

Replaces typing /resolve 34838 into a terminal pane. The agent reads every thread and recommends what to do about each one; you go through them and decide. Panels are drawn at the centre pane's true size, 854 × n.

Nothing is written until you handle the thread. Triage reads code, it never edits it. Where a change is the right answer the agent brings a proposed diff and you accept it — so a straightforward thread is one keystroke, and it is still your keystroke.

Colour follows the app's existing rule — if it needs you, it changes colour; quiet states do not narrate themselves. Amber marks the recommendation and staged work. A verdict is a label, never a colour: it is not urgency.

1b

What actually gates resolve

Not CI, and not a develop conflict. Those are signals about a future merge — they do not touch the apply/push machinery, which works on your branch's own history. So a red or conflicting PR opens to cards like any other; the header shows the state and offers /green as a shortcut, never as a wall. You can answer a comment about one file while an unrelated check is red.

What gates is the worktree not being ready to receive a clean commit, because the whole design rests on the tree being clean until the final action. Three states, one screen:

Resolve commits the changes you accept; work already sitting in the tree would be swept into that commit, so "only what you approved" would stop being true. Clear the tree and this opens to the threads.

Commit and stash are one click each; the shell is for anything more. commit… asks for a message and commits the tree as-is; stash is git stash, which you pop yourself later (the daemon does not auto-pop — popping onto a branch the review just amended can conflict, and silently juggling your work is worse than leaving it where you put it). Either clears the tree and opens the threads.

The same screen, different reason, in two more cases. A stopped rebase — the tree is mid-conflict-resolution and cannot take a patch (already tracked as Inner.rebasing). And a running /green — it rewrites this very worktree, so the two are mutually exclusive: the gate reads "resolve opens when /green finishes," and starting /green during a review is refused from the other side. All three are "the tree is not mine to write to yet."

2

What it found

A shape-of-the-work screen, not a summary of things already done. It exists to tell you how long this will take and where the hard part is — two you can wave through, one that wants thinking about.

Three of these four get a card below; the fourth — renovate.json5:188, marieke's — is straightforward with a diff ready, and gets skipped anyway because you ran out of time. It shows up on the final screen as unhandled, which is what skipping a perfectly answerable thread looks like.

The header is an offer, not a verdict. This PR's checks are failing and it is 3 behind develop — and you are reviewing it anyway, because neither gates. The state is named and /green sits right there for when a thread's fix also wants CI work, but it never stops you answering. The rail's dot is on screen throughout; the header earns its place by separating failing from conflicting, which one dot cannot.

The queue is in GitHub's Files-changed order — by file, then line. That is not an invented ordering: GitHub's API hands threads back chronologically, jumping between files, but the Files tab renders them in the diff's order, and a diff's file order is a plain path sort. Sorting by position reproduces the view people actually review in. It also puts the two comments six lines apart in one file back to back, where the second usually changes what you should say to the first. Outdated threads report no line, so they sort on the line they were originally left at.

One control, not two. The stance, the words and the edit used to be separate — buttons on top, a draft box underneath — which let you pick reject and send text that agreed. Now they live together, so choosing is deciding all three at once. The right-hand label says what each costs: thumbs up, reply, change + thumbs up, change + reply.

"Apply" is worded identically on every card, with the same respond with thumbs up under it. It is the option you will pick most often, so it should be recognisable by shape rather than read each time — the specifics of what it writes are in the diff underneath, where they belong.

Every card ends the same way: … / Manual / Say something else. The agent's drafted positions come first, then two fixed escapes — Manual for "I will write this myself", Say something else for "my words, my stance, no code". That second one exists because editing another option's text cannot express disagreement: the does label would still promise a patch, which is exactly the do-A-say-B mismatch one merged control was built to prevent. So the stance you take must be a slot, not a rewrite.

Skip is not in the list. It sits in the action bar on every card, because positions answer how are you handling this and skipping is I am not. Keeping it out also keeps the list to four or five rows rather than five or six.

CONTINUED means you already replied here and they came back. Deliberately not "re-review" — that is GitHub's phrase for requesting a fresh review, which the final panel already uses. Your own comments are set apart in the chain because on a thread like this the thing that matters most is what you committed to last time: the new reply has to be consistent with it, in public, in front of the person who remembers. The read leads with that rather than treating the comment as a fresh ask.

Edits survive switching options. Type into one, click another to look at it, come back — your words are still there, kept per (thread, option) rather than per thread. Anything else makes looking at a second option a punishment for having started typing. Options stay collapsed, so comparing them is still a matter of expanding each in turn; that is the accepted cost of not letting a long diff push the choices off screen.

Two things come with persistence. An edited tag, because on returning to a card the first question is "is this my wording or the agent's?" and the posted footer cannot answer it. And revert to draft, shown only once the text actually differs, so experimenting is reversible and the control never offers to undo nothing.

The reply box is a `<textarea>`, not a contenteditable. The text goes to GitHub as plain markdown, so rich paste is pure liability, and browsers insert <div>/<br> where a newline belongs. openEditor() settled this already. While it has focus the overlay's bare keys — enter, j/k, digits — are suspended, or a reply containing "check the job" would jump cards mid-sentence. esc blurs the box rather than closing the overlay and losing what you typed.

The amber strip is comments that landed after your queue was built. They are deliberately not appended to it — a new thread has had no triage behind it, so it would arrive with no proposed patch, no options and no read, a visibly worse card in the middle of good ones, and "4 of 4" would keep moving. The queue stays the set you agreed to work.

The important half of that strip is the last clause. Missing a new comment mostly means you handle it next session; the exception is re-request, which asserts "everything of yours is addressed" and would be a lie. That does not need special handling — the post step derives re-requests from a fresh fetch, so a new thread counts as open and holds its author back on its own, with the "held back by…" row naming why. The strip just tells you before you wonder.

Resolve and `/green` never run together. Both rewrite the same worktree, so rather than trying to interleave them the overlay makes them exclusive: a running `/green` gates resolve (the intake becomes "resolve opens when it finishes"), and an open review refuses a `/green` start from the other side. That is stricter than an earlier draft, which let `/green` run during review and only blocked the final write — but "the branch is being rebalanced under the diffs I am reading" is not a state worth the subtlety.

"I'll pick it up in a follow-up PR" is a promise with nothing behind it. A story link is a promise with a tracking number, so filing one is the recommendation whenever the point is fair but out of scope — which is most of what lands in a review summary. The reply then says something checkable instead of something reassuring.

{story} is a placeholder, and that is load-bearing. The id does not exist until the story is filed, so the reply cannot be finished in advance — the post step creates the story first, substitutes the id, then posts. Showing the token rather than a fake number keeps the card honest about the order.

There is no change + reply here — a comment with no anchor has no line to patch, so an option that writes a diff would be guessing where. Code, if it is really wanted, goes through Manual.

Skip is worth reaching for more often here. On an anchored thread it is a fallthrough; on a bare remark "read it, noted, nothing owed" is frequently the right answer. It stays in the action bar rather than the option list all the same — positions answer how are you handling this, and skipping is I am not.

ctrl+enter to send · enter does nothing here

Enter is dead on this screen. Across the cards it means "accept this one thing", and here there is no one thing — it is the whole batch. Rather than bolt a guard onto a binding that was trained to feel safe three cards running, the binding simply does not exist: ctrl+enter sends, which is what GitHub's own comment box uses, so it is already in the right hands' muscle memory.

The button names what leaves, not what it does. "Write, push and post" describes mechanics; push 1 commit · file 1 story · post 4 names every outward-facing thing and counts each. That, plus the panel above it, is what makes this screen read differently at a glance from every staging action before it.

APPLY is present tense on purpose. Nothing is applied at this point — not on the branch, not even in the working tree. The row says what the button is about to do, so the list reads as a plan you are approving rather than a receipt for work already done. A thread answered with words only shows REPLY instead.

Pre-commit runs here, not per card. Batching it means one hook run instead of three, and it is the last gate before the push — if it fails, nothing has been posted yet and the whole set is still recoverable.

6

Manual — the phase that waits for you

Manual means: none of these fit, I will write this myself. A comment is required before it posts — without one a Manual thread does nothing on GitHub and is indistinguishable from a skip, except in your own head. The reviewer would get a commit and silence.

The hard part is the code. Propose-only rests on one invariant — the working tree stays clean until the final action — and editing by hand breaks exactly that. Recording the thread and letting your edits ride along with the batch was the cheap answer, and it was rejected: the commit would sweep up whatever you happened to have touched, so "exactly what you approved" stops being true and the file list cannot be complete.

Don't reconcile your edits with pending patches — order them. The accepted patches are written and committed first; then you work on a tree that already reflects every other decision, which is often why this thread needed hands. Nothing to merge, because nothing is pending.

Shown on a different PR (#34875) than the rest of this walkthrough: moving a query into a repository illustrates why a thread wants hands, where #34838's config tweaks do not. Note also that this phase only exists when a thread was answered Manual — #34838 has none, which is why its final screen goes straight to the push.

Two things fall out for free. You cannot describe work you have not done, so the comment is written here, after the fact, rather than guessed at on the card — the card's box becomes a draft you finish. And git diff shows exactly what you touched, so the file list stays complete and the batch is still only what you approved.

The cost is that "one go" breaks. Choosing Manual inserts a screen that waits for you, so the final action is no longer a single button. That is inherent to asking for a human step, not a flaw in the shape — but it is a property the design deliberately bought, and this spends it.

The easy failure, and worth drawing precisely because it is easy: it happens before the push, so nothing left the machine. The daemon cannot fix a lint error — that needs you or an agent — so it stops, rolls the worktree back, and says so. Every decision you made is still staged.

A hook that reformats rather than fails is the same problem wearing a hat. If pre-commit rewrites more than the diff you approved, what lands is not what you read on the cards — so that case stops here too, showing the extra delta, rather than absorbing it quietly.

8

When posting fails halfway

The hard one. Push succeeded, so the code is public and cannot be taken back; then a reply failed. The panel's whole job is to separate what is now irreversibly true from what is still pending, before it offers to do anything.

Retry is not a second code path. It re-fetches the threads and works out what is still missing — the same derivation that produced the original list. So it is correct after a crash, a restart, or a week later, and there is no separate resume logic to get subtly wrong.

A filed story is the one thing GitHub cannot tell us about. Everything else is re-derivable — a reply either exists in the thread or it does not. A story lives in Shortcut, so if the id were forgotten a retry would file a duplicate. It is therefore recorded against the thread the moment it is created, and the retry reuses it. This is the single exception to "derive, do not remember", and it exists because the source of truth is a different system.

"Cannot be unsent" is stated, not implied. The one thing a person needs from this screen is to know which half of the list is now someone else's notification — showing that as a plain sentence beats a green tick they have to interpret.

·

Decisions worth arguing with

Triage proposes, it does not apply. The earlier version had the agent edit and push the easy ones before you saw anything, which is what the skill does in a terminal — but behind a one-click button that is code changing hands without a decision. Proposing costs one extra keystroke per thread and buys back the property that nothing happens you did not choose.

Every thread gets a card, including the boring ones. Auto-handling the obvious ones sounds like a kindness until the one it got wrong is already pushed. A recommendation plus Enter is nearly as fast and fails safe.

The read sits above the positions, not beside the comment. You read the reviewer in their own words first and the agent's opinion second, immediately before choosing.

Outdated is a flag, not a filter. The rail's unresolved count excludes outdated threads so they cannot gate a button; triage keeps them, because the code moved but the point may still stand.

The footer is shown but not editable. It sits under the draft as a dim line rather than as text in the box, so it cannot be half-deleted into something that reads as yours.
